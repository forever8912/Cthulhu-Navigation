> 版本：v1.0（2026-10-30）
> 状态：现行协作细则

## 一、协作目标

多 Agent 的目标不是“同时写更多代码”，而是：

1. 让不同任务拥有清晰边界和唯一 Owner。
2. 让每个结果都能独立验证、撤销和审查。
3. 避免多个 Agent 同时改公共文件造成隐性冲突。
4. 保持策划、配置、代码、美术和测试使用同一事实来源。

当前阶段优先并行的是“可独立交付的侧向工作”，不是互相等待的核心链路。

## 二、角色与责任

| 角色 | 决策权 | 主要产出 | 禁止事项 |
|---|---|---|---|
| 集成负责人 | 架构边界、公共协议、规范与合并裁决 | 任务拆分、公共接口、合并、发布候选 | 同时承担所有实现任务 |
| 系统设计 Agent | 单系统规则与验收建议 | 规则差异、状态机、边界用例 | 静默改核心范围或经济目标 |
| 战斗 Agent | 战斗模块内部实现 | tick、索敌、伤害、怪物状态、测试 | 引用 UI Node；按怪物 ID 写特判 |
| 船舱 Agent | 船舱模块内部实现 | 岗位、生产、仓容、修理、测试 | 改战斗公共协议而不通知 Owner |
| 数据 Agent | 配置协议与导出链 | Schema、导出器、校验、类型生成 | 手改生成 JSON；吞掉阻断错误 |
| UI Agent | 表现与交互 | Prefab、View、动效、触控验证 | 在 View 中重写业务规则 |
| 美术 Agent | 美术源资产与记录 | DRAFT/REVIEW 资产、manifest、验收表 | 直接覆盖 APPROVED；改风格方向 |
| QA Agent | 独立验证 | 测试报告、复现、性能基线 | 默认不修改产品代码；不得自行降低验收标准 |

同一人或同一模型可以先后承担多个角色，但同一个任务周期内必须明确当前角色。

## 三、任务卡：没有任务卡不得派发

每个 Agent 的输入必须包含以下字段：

```text
任务编号：例如 VS-W2-BATTLE-01
角色：战斗 Agent
目标：一句话说明可观察结果
背景：只给完成任务所需上下文
必读文件：最多 4 份
允许写入：精确到目录或文件
禁止写入：公共文件、其他模块、生成物等
依赖输入：接口、配置、资产版本
交付物：代码/配置/文档/资产/报告
验收条件：可运行、可测量、可复现
验证命令/步骤：由谁执行、在哪里执行
风险：已知不确定项
非目标：明确本次不做什么
```

任务目标必须描述行为，不得只写“完善战斗”“优化 UI”“做一些怪物”。

合格示例：

> 实现固定 20Hz 的怪物接近与射程判定。给定同一 seed 和配置，运行 300 tick 的结果必须完全一致；只写 `logic/battle/movement` 与对应测试，不接 Cocos 节点和动画。

## 四、任务拆分方法

### 4.1 按依赖方向拆，不按文件数量拆

推荐依赖顺序：

```text
配置 Schema
    ↓
纯逻辑接口与测试夹具
    ↓
系统实现
    ↓
表现层适配
    ↓
美术/音效接入
    ↓
集成与真机验收
```

上游接口未冻结前，下游 Agent 可以做 mock 和原型，但不得把临时协议当正式协议合并。

### 4.2 适合并行

- 战斗纯逻辑与厚涂母版探索。
- 配置校验与 UI 灰盒。
- 存档迁移测试与非相关美术资产。
- QA 编写验收用例与实现 Agent 编码。
- 不同怪物/房间的源资产制作，前提是母版已 APPROVED。

### 4.3 不适合并行

- 多个 Agent 同时定义公共战斗快照。
- 数据 Agent 和系统 Agent 各自发明配置字段。
- UI 与逻辑在接口未冻结前同时改同一个状态结构。
- 多个美术 Agent 在风格母版未批准前批量生成资产。
- 两个 Agent 同时修同一个缺陷。

## 五、接口冻结与变更提案

以下内容视为公共协议：

- 配置 Schema、ID、枚举和事件结果类型。
- `BattleSnapshot`、`ShipSnapshot` 等跨层数据结构。
- 存档结构与版本号。
- 平台服务接口。
- 资源命名、锚点、画布和 manifest 字段。

公共协议变更使用以下模板：

```text
提案编号：RFC-模块-序号
现状问题：
拟议变更：
受影响文件/Agent：
兼容策略：
存档/配置迁移：
替代方案：
验收方法：
```

未批准 RFC 不得进入共享分支。紧急修复也必须在提交说明中补齐影响与兼容策略。

## 六、分支、工作区与提交

### 6.1 分支约定

```text
main                          稳定集成线
agent/<任务号>-<短名称>       单 Agent 任务分支
release/vs-<版本>             垂直切片发布候选
```

- 并行写入任务必须使用独立 worktree 或独立克隆。
- 文档仓和代码仓分别维护基线；分支必须从对应仓库由集成负责人指定的基线创建。
- Agent 不能私自合并其他 Agent 分支来“解决依赖”。
- 跨仓任务必须拆成两个可审查提交，并在交接报告中分别列出哈希与依赖顺序。

### 6.2 提交约定

```text
feat(battle): add deterministic range targeting
fix(save): migrate room durability to save v2
test(config): reject duplicate monster ids
art(monster): add approved monster 101 part set v003
docs(agents): clarify shared interface ownership
```

- 每次提交必须可编译或明确标记为仅文档/仅源资产。
- 不提交本地缓存、构建输出、账号会话和临时截图。
- 不得用“update”“修改”“misc”等无法审查的提交信息。

## 七、审查等级

| 等级 | 适用内容 | 最低审查要求 |
|---|---|---|
| R0 | 文字澄清、无行为变化 | 结构和链接检查 |
| R1 | 单模块内部实现 | Owner 自测 + 独立 Agent 代码审查 |
| R2 | 公共接口、配置 Schema、存档、平台层 | 集成负责人审查 + 自动测试 + 兼容说明 |
| R3 | 核心玩法、经济规则、发行合规、美术风格母版 | 用户/主理人确认 + 原型或对照证据 |

任何 Agent 不得自行把 R2/R3 变更降级为 R1。

## 八、集成流程

集成负责人按以下顺序处理：

1. 确认任务卡验收项和写入范围。
2. 阅读 Agent 交接报告，不先看结论标签。
3. 检查 diff 是否包含越界修改。
4. 运行类型检查、单测、配置校验。
5. 运行最小可玩路径或真机步骤。
6. 检查存档、配置与资源兼容性。
7. 合并后再次运行共享基线测试。
8. 更新里程碑状态与相关 SSOT。

多个分支的推荐集成顺序：Schema/类型 → 纯逻辑 → 表现层 → 资产 → QA 修复。

## 九、冲突处理

### 9.1 代码冲突

- 不以“让编译通过”为唯一目标手工拼接冲突。
- 先确认哪一方拥有接口决策权，再由 Owner 生成合并版本。
- 若两边都改变行为，先写失败用例固定预期，再合并实现。

### 9.2 文档冲突

- 优先修 SSOT，再修引用文档。
- 历史文件不反向覆盖现行决策。
- 无法判断时在索引中登记待定，不制造第三种口径。

### 9.3 美术冲突

- APPROVED 版本不原地覆盖。
- 两个候选版本并存时使用不同版本号，由美术审查选定。
- 选定后旧版进入 `deprecated`，不得直接删除追溯信息。

## 十、缺陷处理

缺陷报告至少包含：

```text
缺陷编号：BUG-模块-序号
版本/提交：
环境：Web / 真机型号 / 平台工具
前置状态：
复现步骤：
预期：
实际：
复现率：
截图/日志：
严重度：阻断 / 严重 / 一般 / 轻微
```

修复 Agent 只修改复现所需最小范围，并补充能防止回归的测试或真机步骤。

## 十一、每周协作节奏

| 时间 | 活动 |
|---|---|
| 周初 | 冻结本周任务卡、Owner 和公共接口变更 |
| 每个任务开始 | Agent 声明写入范围与验收条件 |
| 每个任务结束 | 交接报告 + 可审查提交 |
| 周中 | 集成一次，尽早发现接口偏差 |
| 周末 | 生成可启动版本、运行基线验收、清空未决冲突 |

如果一周结束没有可启动版本，下周所有 Agent 停止新增功能，只修复集成与技术债。

## 十二、规范迭代流程

规范建议先登记在本文件末尾的候选区，经过一次真实任务验证后再升为强制规则。

变更记录格式：

| 版本 | 日期 | 变更 | 原因 | 影响与迁移 |
|---|---|---|---|---|
| v1.0 | 2026-10-30 | 建立多 Agent 任务卡、Owner、审查与集成规则 | 准备进入代码制作 | 新任务立即生效，历史文档不要求返工 |

候选规则不得被 Agent 当作硬要求，除非任务卡明确引用。
